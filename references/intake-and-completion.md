# Intake and completion

## Ask before delivering findings

Keep analytical order separate from conversational order: collect the necessary profile first, assess the package independently, then apply the profile. A single final report can contain two independent rounds.

1. Reuse the current request and context the host already exposes. Do not search private memories/conversations for a profile. Tag requirements as user-stated, host-observed, or inferred; installed defaults do not prove personal preferences.
2. Explicit generic-only/quick screening: no Round 2 questions. Known personal use case: ask only unresolved decision-changing gaps. Open-ended evaluation without context: one compact intake, for example: “Is this general research, adding a capability, or replacing an existing workflow? If personal fit matters, tell me the main task/output and host/OS; mention any hard data or permission limits.” Adapt to the candidate after a brief read if needed; do not demand every profile field.
3. While awaiting an answer, perform independent read-only inspection when the host permits. Avoid releasing a complete baseline followed by a routine second-round questionnaire. If the user explicitly wants staged results, honor that choice.
4. With a sufficient answer, finish both selected rounds without a new permission-to-continue prompt. Optional unknowns become assumptions, NE, or conditional branches. Silence never grants installation, account access or publication. If no answer is available when the turn must end, deliver supported Round 1 and mark Round 2 not assessed; do not fabricate fit.
5. Ask again only for a newly discovered material ambiguity that prevents a responsible conclusion or a required authorization. Otherwise record the limitation and a bounded next check. An installed-skill inventory is read-only; a review does not require persistent memory writes.

## Completion check for standard/deep reports

Before delivery, verify the result against this checklist; repair omissions rather than asking the user whether to finish.

- Revision/date/scope and inspection coverage identify fully read files, sampled sections and uninspected material. Listing files or counting lines is not reviewing their contents.
- Each decisive claim has an evidence ID and retrievable source locator. Separate source-code facts, reported observations, inferred mechanisms and live production behavior. Search snippets or several derivative articles do not establish independent primary-source verification. If the exact primary code/version cannot be checked, label the claim unverified or corroborated secondhand; do not say “safe to rely on.”
- Doctrine review distinguishes the strongest thesis, assumptions, counterexamples and limitations; architecture traces input → routing/tools/state → output → verification/recovery. Give strengths as well as defects. Evaluate prompt packages on instruction behavior, not an arbitrary requirement for executable code or unit tests.
- Findings have severity, confidence, trigger, consequence and proportionate remedy. Distinguish a default/example from an enforced rule. A risk is not an observed incident. Missing gitignore is an accidental-commit risk, not proof of disclosure. Explain whether an apparent naming mismatch actually violates a supported host requirement before making it a release blocker.
- Numerical reasoning states the disputed proposition. Showing that an intervention does not reach a threshold does not by itself refute a narrower “helps” or “highest ROI” claim; the latter needs costs and outcomes. Do not replace an unsupported assertion with an equally unsupported counterclaim.
- Ten Round 1 categories and, when assessed, six Round 2 categories have score/NE/NA, confidence, evidence, scope and rationale. Keep gates consistent with the verdict; do not drop score columns to shorten a report.
- Round 2 includes an acceptance matrix with expected versus actual results and passed/failed/not tested/blocked/not applicable. A prompt-only fixture may be feasible without installing the candidate; distinguish that from host discovery/integration or real-account testing. Never treat installation as universally necessary for behavioral evaluation.
- Overlap conclusions distinguish metadata shortlist, inspected capability and observed behavior. Similar descriptions imply possible overlap, not proven equivalence or definite routing failure. Include consolidation benefits (fewer handoffs, simpler maintenance), not only duplication costs. Without comparative evidence, “only incremental value” and “every scenario conflicts” are too strong.
- Verdicts match evidence strength. A conditional “retain existing pending a bounded comparison” may be defensible where a categorical rejection is not. Suggested extracted sources must themselves be checked before reuse.
- A short summary links to the complete HTML artifact. Local/private delivery is distinct from publication. Public exports contain only generic material reviewed for disclosure. No user profile, raw conversation/tool transcript or private inventory enters the skill repository.
